# 판 기록 로그 설계 (2026-11-23)

## 왜 하는가

밸런스 패치 근거를 실제 플레이에서 얻는다(사용자). 보고 싶은 것:
- 자주 쓰는 도깨비, 잘 안 쓰는 도깨비, 부족한 도깨비(필요했는데 끝내 못 구한 재료)
- 깬 판 기준으로 성능이 좋은 도깨비와 안 좋은 도깨비

일단 일주일 동안 로그로 JSON을 쌓고, 그 안에 같이 분석한다(사용자 결정). DB는 쓰지 않는다.

## 검토한 방식

1. **판 기록(시드 + 입력)을 남기고 분석할 때 다시 돌리기 (선택):** 지표를 나중에 더해도 이미 쌓인 판에서 뽑힌다. 게임 상태를 건드리지 않아 판 해시와 리플레이가 그대로다. 서버는 저장만 한다.
2. 통계를 계산해서 남기기: 만들기 쉽지만 항목이 고정되고, 솔로는 브라우저에 집계 코드가 따로 필요하다.
3. 콘솔 한 줄 로그만 늘리기: 분석용으로 부족하다.

## 만드는 것

- **온라인:** 판이 끝나면 서버가 `recording()`(시드·자리·모든 입력·커밋·데이터 버전)과 요약을 로그에 찍는다.
- **솔로:** 브라우저가 판 동안 명령을 틱 번호와 함께 모아 두고, 끝나면 `POST /api/solo-log`로 보낸다. 서버는 같은 형식으로 찍는다. 본문 크기 상한은 1MB(내 판단). 솔로 판을 다시 돌리는 `replayGame`을 만들고, 기록이 같은 결과로 다시 돌아가는지 시험한다.
- **요약 (바로 셀 수 있게):** 무작위 판 id, 모드(솔로/온라인), 단계, 난이도, 인원, 결과, 도달 라운드, 걸린 시간, 데이터 버전, 자리마다 판 끝 보드·보관함 유닛 id 목록과 깼는지 여부. 이름은 넣지 않는다.
- **형식 (내 판단):** `[판 기록] <id> <json>`. 판 기록은 gzip + base64로 줄인다. 한 줄이 8KB를 넘으면 `[판 기록 2/3] <id> ...`처럼 나눈다.
- 연습판(`devJumpTick`)과 개발 모드 판은 남기지 않는다.

## 분석 (일주일 안에, 이번 작업 범위 밖)

기록을 시뮬레이터로 다시 돌려 아래를 CSV로 뽑는다. 데이터 버전별로 나눠 패치 전후를 섞지 않는다.

| 지표 | 계산 |
|---|---|
| 자주 쓰는 도깨비 | 보드에 있었던 라운드 수, 판 끝 보드에 남은 비율 |
| 잘 안 쓰는 도깨비 | 만든 횟수, 만들자마자 팔거나 재료로 바로 쓴 비율 |
| 부족한 도깨비 | 판 끝에 가장 가까운 6단계 조합에 모자란 재료 |
| 성능 | 깬 판 기준 유닛별 피해량, 보드에 있던 1초당 피해량(등급별 비교), 보스·역신 피해 비중, 깬 판과 못 깬 판의 포함 비율 차이 |

성능은 보드에 있던 시간과 등급으로 나눠 비교한다. 사람이 고른 조합이라 많이 쓴 유닛이 좋아 보일 수 있으니, 판 수가 적을 때는 경향으로만 본다. 패치 후보는 시뮬레이터로 먼저 시험한다.

## 주의

- Render 무료 요금제의 로그 보관 기간(7일쯤으로 알고 있으나 확인 못 함)과 한 줄 길이 제한은 확인하지 못했다. 첫 배포 뒤 한 판으로 잘림 여부를 확인하고, 며칠마다 로그를 받아 둔다.
- 서버가 재시작할 때 진행 중이던 판은 기록되지 않는다.
- 솔로 기록은 조작할 수 있다. 분석할 때 다시 돌린 결과가 요약과 다르면 버린다.

## 하지 않는 것

DB, 대시보드, 분석 스크립트(분석 때 만든다), 플레이어 이름이나 식별 정보.
